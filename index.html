Transaction lifecycle

Suggested event flow for a real chain integration.

1. Validate request

Backend validates user permissions, stock rules, and invoice uniqueness.

2. Create transaction record

Backend creates a canonical payload and SHA-256 fingerprint.

3. Submit on-chain

Smart contract records the approved event or its fingerprint.

4. Confirm and reconcile

Backend stores transaction hash, block number and confirmation status.

Expected API contract

Suggested contract for wiring this UI to your backend. Update api.js functions to match your actual server.

GET /healthReturns {"status":"ok"} and optionally network status.
GET /inventoryReturns an array of material records with id, name, quantity, unit, cost, reorderLevel.
GET /transactionsReturns movement records with id, type, material, qty, approval, hash, previousHash, blockchainTxHash.
POST /transactionsAccepts a stock movement request; server validates and returns the created record.
POST /transactions/:id/approveApproves a pending record after authorization. Enforce permissions server-side.
POST /transactions/:id/rejectRejects a pending record and records reviewer/reason.
Supplier paymentsRecommended endpoints: GET /payments?poId=..., POST /payments, POST /payments/:id/verify, and a backend-to-contract payment-event anchoring service.
Purchase ordersRecommended endpoints: GET/POST /purchase-orders, GET /purchase-orders/:id, POST /purchase-orders/:id/receipts, POST /receipts/:id/approve, GET /reconciliation.
